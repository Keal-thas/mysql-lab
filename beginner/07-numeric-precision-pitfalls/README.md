# 长数字/长字符串"看起来不一样、比出来却一样"

## 你会学到什么

存了两个明明不一样的长数字或长字符串（比如订单号、身份证号、雪花算法生成
的 ID），结果一查发现它们"相等"了，或者一条查询条件意外命中了好几行——这种
诡异现象背后至少有四种不同的原因，这个 demo 把它们逐一复现出来，教你怎么
根据现象反推是哪一种。

## 原理

- **原因一：`FLOAT`/`DOUBLE` 精度丢失**。这两个类型底层是二进制浮点数，能
  精确表示的十进制有效数字是有限的——`FLOAT` 大约 7 位，`DOUBLE` 大约
  15~17 位。存一个超过这个位数的长整数，会被自动四舍五入成"这个类型能表示
  的、离它最近的值"，两个原本不同、但差异出现在"能表示范围之外"那几位的
  数字，舍入之后就变成了同一个值。这不是 MySQL 的 bug，是所有用二进制浮点数
  的语言/数据库通用的限制。
- **原因二：`INT` 整数溢出截断**。`INT` 能精确存到约 21 亿（10 位数），存一个
  14 位的数字，超出范围的值会被"夹"到类型的边界值（比如 `INT` 的上限
  `2147483647`），两个都超范围的不同数字，夹出来的结果可能一样。
- **原因三：`VARCHAR`/`CHAR` 长度截断**。列定义的长度不够，超出长度的部分被
  直接砍掉，两个长字符串砍完剩下的前缀部分可能一样。
- 原因二、三**默认情况下不会静默发生**——这个仓库（跟 MySQL 5.7 起的默认值
  一样）开着 `STRICT_TRANS_TABLES`，普通 `INSERT` 遇到溢出/截断会直接报错拦
  下来，不会让坏数据进库。会绕过这个保护的常见情况：`sql_mode` 被手动关掉了
  严格模式（老项目为兼容旧代码很常见）、数据库版本是 MySQL 5.6 或更早（默认
  就是非严格模式）、用了 `INSERT IGNORE`/`LOAD DATA` 这类把错误自动降级成
  警告的写法。
- **原因四：`VARCHAR` 本身存的是精确值，但查询时触发了隐式类型转换**。哪怕
  列里存的字符串完全正确、`SELECT` 出来两行明明不一样，只要 `WHERE` 条件里
  拿一个**不带引号**的数字去比较，MySQL 就会把这一整列的值都转成 `DOUBLE`
  再比——原因一的精度丢失问题在这里重新出现，即使存储层面从来没丢过任何
  数据。这跟 [隐式类型转换让索引失效](../03-implicit-type-conversion/)
  是同一个坑的另一种表现形式：那边讲的是索引失效，这里讲的是查出多余的行。

## 复现

```bash
../../client.sh < demo.sql
```

四段依次对应上面的四个原因，每段都会打印"看起来不同的两个值"和"比较/查询
结果"，可以直接对照实测输出：

| # | 原因 | 现象 |
|---|------|------|
| 1 | FLOAT/DOUBLE 精度丢失 | 17 位数存 FLOAT、18 位数存 DOUBLE，两个不同的数比较结果为 `1`（相等） |
| 2 | INT 溢出截断 | 14 位数存 INT（`INSERT IGNORE`），两行都变成 `2147483647` |
| 3 | VARCHAR 长度截断 | 17 位字符串存 VARCHAR(10)（`INSERT IGNORE`），两行都变成同一个 10 位前缀 |
| 4 | VARCHAR 查询隐式转换 | 列里存的是精确的 18 位字符串，`WHERE col = '...'`（带引号）只中一行，`WHERE col = ...`（不带引号）两行都中 |

## 结论

- 遇到"两个看起来不同的值比出来却相等"，先去确认列的真实类型和长度：
  ```sql
  SELECT COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH, NUMERIC_PRECISION
  FROM information_schema.columns
  WHERE table_schema = '你的库' AND table_name = '你的表' AND column_name = '那一列';
  ```
  `DATA_TYPE` 是 `float`/`double` → 精度丢失；是 `int`/`bigint` 但
  `NUMERIC_PRECISION` 覆盖不了数据位数 → 溢出截断；是 `varchar`/`char` 但
  `CHARACTER_MAXIMUM_LENGTH` 比数据短 → 长度截断；类型和长度都没问题 → 大概率
  是查询语句触发了隐式转换（原因四）。
- 订单号、身份证号、手机号、雪花 ID 这类"长得像数字、但从不参与数值计算"的
  标识符，一律用 `VARCHAR`/`CHAR` 存，**并且查询时永远给值加引号**——原因四
  说明了光选对存储类型还不够，查询写法本身也可能重新引入同样的坑。
- 真的需要存超大整数并参与数值计算（比如金额、计数器），用 `BIGINT`（精确到
  19 位）或 `DECIMAL`（任意精度，但更慢），永远不要用 `FLOAT`/`DOUBLE`
  存整数标识符或货币金额。
