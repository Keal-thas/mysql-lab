# ORDER BY 在有相同值时顺序不固定

## 你会学到什么

`ORDER BY` 只保证结果按你指定的列排序。如果排序列里有重复值（"平局" / tie），
MySQL **不保证**这些并列行之间的相对顺序。很多代码依赖这个"看起来很稳定"的顺序，
换一个索引、换一次执行计划、甚至换一个 MySQL 版本，顺序就可能变了——分页丢数据/
出现重复行的经典 bug，根源往往就在这里。

## 原理

- SQL 标准里结果集本身是无序的，`ORDER BY` 只对写出来的列做排序承诺；没写的部分
  （比如同值的行谁先谁后）完全没有约定。
- MySQL 实际返回的"平局顺序"，取决于执行计划怎么把行读出来：
  - **全表扫描（InnoDB）**：按聚簇索引（主键）顺序读出，因为 InnoDB 表本身就是
    按主键组织的 B+ 树。
  - **走二级索引扫描**：二级索引的叶子节点存的是 `(索引列, 主键)`，重复的索引列值
    内部天然按主键排列。所以正向扫描时平局按主键升序，**反向扫描（DESC）时平局按
    主键降序**。
  - **触发 filesort**：MySQL 把 `(排序键, 行指针)` 取出来自己排序，用的排序算法
    不保证稳定（stable），平局顺序和"原始读出顺序"没有必然关系，只是很多情况下
    实现细节让它看起来保留了原始顺序。
- 这些都是**实现细节**，不是接口契约。索引的增删、优化器选择的访问路径、
  `ANALYZE TABLE` 之后的统计信息、甚至 MySQL 版本升级，都可能在不改一行 SQL 的
  情况下悄悄改变平局顺序。

## 复现

```bash
../../client.sh < demo.sql
```

对照 `demo.sql` 里的注释逐段看结果，重点看第 3 步和第 4 步——**同一张表、同一条
逻辑查询**，k=20 的两行 (`d`, `e`) 顺序是相反的：

- 走索引倒序扫描（`FORCE INDEX` + `Backward index scan`）：`e, d`（按主键降序）
- 强制 filesort（`IGNORE INDEX`）：`d, e`（按主键升序）

这个差异在真实 MySQL 8.4 上是可复现的，不是理论推测。

## 结论：怎么写才对

如果业务逻辑依赖顺序（最典型的是分页 `LIMIT/OFFSET`），排序列组合必须能**唯一**
确定每一行，做法是在 `ORDER BY` 末尾补上主键（或其他唯一列）当 tiebreaker：

```sql
ORDER BY k DESC, id
```

这样无论执行计划怎么变，结果顺序永远确定。
