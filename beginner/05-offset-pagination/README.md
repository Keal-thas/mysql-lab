# 大 OFFSET 分页为什么越翻越慢

## 你会学到什么

`LIMIT 20 OFFSET 100` 和 `LIMIT 20 OFFSET 49000` 看起来只是数字不同，但后者慢
了两个数量级。用户往后翻页时体验会越来越差，这是传统 `OFFSET` 分页在数据量大了
之后的通病。

## 原理

`OFFSET` 不是"直接跳到第 N 行"，MySQL 必须先按 `ORDER BY` 的顺序把前面
`OFFSET + LIMIT` 条数据全部走一遍，再把 `OFFSET` 这部分丢弃，只留最后 `LIMIT`
条返回给你。`OFFSET` 越大，白白扫描、丢弃的行就越多——哪怕这些行最终一条都不会
返回给用户。

解决办法是**游标 / keyset 分页**：不用"第几页"，而是记住上一页最后一条记录的
排序键（比如 `id`），下一页直接用 `WHERE id > 上一页最后的id` 定位，走索引直接
跳到该跳到的位置，不用管前面翻了多少页。

## 复现

```bash
../../client.sh < demo.sql
```

在 5 万行的表上（本地一次实测），`EXPLAIN ANALYZE` 的 `actual time`：

- `OFFSET 100`：约 **0.03ms**
- `OFFSET 49000`：约 **3.5ms**（多扫描/丢弃了约 49000 行）
- 游标分页 `WHERE id > 49000`：约 **0.03ms**，和翻第一页几乎一样快

## 结论 / 怎么写才对

- 如果产品形态允许（大部分"无限滚动"/"下一页"场景都允许），优先用游标分页。
- 如果一定要支持"跳到第 N 页"这种传统页码 UI，`OFFSET` 分页的性能上限就是数据
  量和页码的乘积，需要考虑限制最大页码，或者对排序键做一次子查询先定位再关联。
