# 隐式类型转换让索引失效

## 你会学到什么

`phone` 是 `VARCHAR` 并且建了索引，但 `WHERE phone = 13800012345`（数字字面量，
没加引号）会让这个索引基本失效，即使数据一模一样、SQL 看起来"差不多"。这是生产
上最常见、最容易被忽略的性能坑之一。

## 原理

MySQL 做比较时，两边类型不一致会做隐式类型转换。当列是字符串、字面量是数字时，
MySQL 按照类型优先级把**列**转换成数字（而不是把数字转成字符串），也就是查询等
价于：

```sql
WHERE CAST(phone AS DOUBLE) = 13800012345
```

一旦索引列被包进了一个函数/表达式里，索引上存的是原始的 `phone` 字符串值，没法
直接用来做等值定位——MySQL 只能把索引（或表）整个扫一遍，对每一行都做一次转换
再比较。字面量换成字符串 `'13800012345'`，就不需要转换，能直接走索引做等值查找。

## 复现

```bash
../../client.sh < demo.sql
```

在 5 万行的表上（本地一次实测）：

- `phone = '13800012345'`：走索引直接命中 1 行，`actual time` 约 **0.007ms**
- `phone = 13800012345`：扫描全部 5 万行再逐行转换比较，`actual time` 约 **5.6ms**

差了近 800 倍，而且随着表变大，这个差距只会线性扩大。

## 结论 / 怎么写才对

字符串列一律用字符串字面量比较，尤其是从外部（比如 HTTP 参数、Excel 导入）拿到
的值——很多语言/框架会把看起来像数字的字符串自动转成数字类型，传到 SQL 层就变成
了没加引号的字面量。写 SQL 或者用 ORM/查询构造器时，明确保证类型和列定义一致。
