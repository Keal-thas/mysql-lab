# 慢查询定位与调优思路

## 你会学到什么

一套完整的"生产上发现慢查询 → 定位原因 → 加索引 → 验证效果"的流程，外加一个
很容易让人困惑的现象：**加了索引，`EXPLAIN` 还是显示全表扫描**——这不一定是
bug，可能是优化器算过账之后主动选的。

## 流程

### 1. 先找到慢查询

生产上开启慢查询日志（`slow_query_log`），设置 `long_query_time` 阈值，超过阈值
的查询会被记录下来，包含 `rows_examined`（扫描行数）和 `rows_sent`（返回行数）。
两者差距大，基本就是"扫了很多用不上的行"的信号。

也可以用 `performance_schema.events_statements_summary_by_digest`，按语句"模式"
（参数化之后）聚合统计总耗时、调用次数，找真正拖累整体的查询，而不是揪着某一次
慢查询不放。

### 2. 用 EXPLAIN ANALYZE 确认原因

`EXPLAIN` 之外，`EXPLAIN ANALYZE` 会真的执行一遍，给出每一步的真实耗时和真实
行数，能验证"是不是真的在全表扫描"。

### 3. 针对性加索引，再跑一次 EXPLAIN ANALYZE 验证

### 4. 别忘了看看优化器为什么没用你加的索引

## 复现

```bash
../../client.sh < demo.sql
```

在 5 万行的表上（本地一次实测）：

- 无索引，`status='paid' AND created_at='2024-06-02'`（命中 46 行）：慢查询日志
  显示 `rows_examined=50000, rows_sent=46`；`EXPLAIN ANALYZE` 显示全表扫描，
  `actual time` 约 6ms。
- 加上 `(status, created_at)` 联合索引后，同一条查询：`Index lookup`，
  `actual time` 约 0.07ms——将近 100 倍提升。
- 换一条**选择性差**的查询 `status='paid' AND created_at>'2024-06-01'`（命中约
  9680 行，接近表的 1/5）：即使索引已经建好，`EXPLAIN ANALYZE` 依然显示**全表
  扫描**，耗时约 6.7ms；用 `FORCE INDEX` 强制走索引反而只有约 5ms，优化器选全表
  扫描是合理的，不是没生效。

## 原理：为什么优化器会放弃一个能用的索引

这里的索引是二级索引，命中的每一行都得再回表查一次聚簇索引才能拿到 `SELECT *`
需要的其他列（`note`）。命中的行越多，"回表"这个随机 I/O 的总成本就越高；命中
比例一旦超过某个临界点，还不如直接顺序扫一遍全表来得便宜——这正是优化器基于统计
信息估算出来的结论。命中比例小（选择性好）时索引划算，比例大（选择性差）时全表
扫描反而划算，两者之间没有一个固定的百分比阈值，取决于表结构、行大小、存储引擎
的成本模型。

## 结论 / 怎么写才对

- "有索引 = 一定会被用上"是错的，看 `EXPLAIN`/`EXPLAIN ANALYZE` 才知道真相。
- 如果业务上明知某个条件选择性差（比如状态只有 3 种值，均匀分布），加索引本身
  收益有限，更值得考虑的是覆盖索引（把 `SELECT` 要用的列也放进索引，省掉回表）
  或者调整查询条件、加更细的过滤维度提高选择性。
- 调优是"发现 → 验证 → 修改 → 再验证"的闭环，每一步都要靠 `EXPLAIN ANALYZE`
  这类真实数据说话，不要凭经验加了索引就假设一定有效。
