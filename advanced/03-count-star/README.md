# `COUNT(*)` 优化

## 你会学到什么

"这张表这么大，`SELECT COUNT(*)` 怎么这么慢"是个很常见的问题。跟很多人的印象
不同，MyISAM 会维护一个现成的总行数、`COUNT(*)` 是 O(1)，但 **InnoDB 不会**——
这个 demo 实测 `COUNT(*)` 在 InnoDB 上到底在干什么，以及两种绕开全表扫描的
思路：近似值、维护计数表。

## 原理

- InnoDB 是多版本存储引擎（MVCC），同一时刻不同事务看到的行数可能不一样，
  没法像 MyISAM 那样简单维护一个全局计数器。`COUNT(*)` 不带 `WHERE` 时，
  优化器会挑这张表里**体积最小的索引**整个扫一遍（通常是某个二级索引，
  比全表扫描主键索引省 I/O），但仍然是一次和行数成正比的扫描。
- 带 `WHERE` 条件时，如果这个条件用不上索引，就是标准的全表扫描 + 逐行判断，
  没有任何捷径——这也是为什么这个 demo 里 `WHERE status = 'c'` 比不带条件的
  `COUNT(*)` 慢了十几倍：多扫的是同一张表，但要读取、判断每一行的 `status`
  列，而不只是扫一个瘦索引。
- **近似值**：`information_schema.tables.TABLE_ROWS`（或 `SHOW TABLE STATUS`）
  是优化器统计信息里记的行数估算，不需要真的扫表，几乎零成本，代价是不准确
  （实测样例里几百万行时误差在千分之几量级，写入越频繁、`ANALYZE TABLE` 跑
  得越少，误差可能越大）。适合"首页展示一个大概的总数"这种不需要精确值的
  场景。
- **维护计数表**：业务代码在 `INSERT`/`DELETE` 的同时手动（或用触发器）维护
  一行计数器，读的时候直接查这一行，天生 O(1)、绝对精确。代价是每次写入都
  多了一次 `UPDATE`，而且这行计数器本身容易成为热点（高并发写入下这一行的
  锁竞争可能比原表的写入本身还激烈，实际生产里常见的优化是把计数器分片成
  多行、读的时候再 `SUM()`）。

## 复现

```bash
../../client.sh < demo.sql
```

`demo.sql` 依次跑四段：

1. `COUNT(*)` 不带条件——`EXPLAIN ANALYZE` 里能看到 `Count rows in events`，
   耗时在十几毫秒量级（200 万行）。
2. `COUNT(*) WHERE status = 'c'`（无索引列）——变成 `Table scan`，耗时是
   (1) 的十几倍。
3. `information_schema.tables` 里的近似值 vs 真实的 `COUNT(*)`——前者几乎
   瞬间返回，跟后者相差在千分之几以内。
4. 建一张 `counters` 表 + 两个触发器，做几次 `INSERT`/`DELETE`，对比
   `counters.cnt` 和真实 `COUNT(*)`——两边数字应该始终一致，但前者是主键
   查找、后者是全表扫描。

## 结论

- 精确又快是不可兼得的：要精确，要么忍受和数据量成正比的扫描耗时，要么在写
  路径上多付出维护计数器的成本；要快又不想改写路径，只能接受近似值。
- 选哪种方案取决于业务：用户看的"约 xx 万人关注"用近似值就够；库存扣减这种
  必须精确的场景，维护计数表（或者直接把库存字段当计数器，而不是每次
  `COUNT(*)` 统计还剩多少）更合适。
- 如果条件本身能用上索引（比如按状态建个索引），`COUNT(*) WHERE ...`
  会退化成索引扫描而不是全表扫描，性能差距会小很多——遇到慢的 `COUNT`
  查询，先看 `EXPLAIN` 走没走索引，不要一上来就跳到近似值/计数表这类更复杂
  的方案。
