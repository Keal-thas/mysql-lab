# 分区表：适用场景与注意事项

## 你会学到什么

分区表不是让单条查询变快的万能索引，它的核心价值是"整块整块地管理数据"——
最典型的场景是按时间分区的日志/流水表，定期把过期的分区整个丢弃，而不是跑一
条巨大的 `DELETE`。这个 demo 实测两件事：分区裁剪什么时候生效/失效，以及
`DROP PARTITION` 比普通 `DELETE` 快多少。

## 原理

- `PARTITION BY RANGE (YEAR(created_at))` 把一张表在物理上拆成好几个独立的
  子表（分区），每个分区按定义好的范围存一部分数据。**分区键必须包含在每个
  唯一索引里**——本例的主键写成 `(id, created_at)` 而不是单独的 `id`，就是
  为了满足这个要求，这也是分区表最容易踩的第一个坑：给已有表加分区，可能因为
  这条限制被迫改主键。
- **分区裁剪**（partition pruning）：`WHERE` 条件如果能让优化器直接推断出
  "只可能命中哪几个分区"，`EXPLAIN` 的 `partitions` 列就只会列出那几个，
  没命中的分区连扫都不扫，等于免费获得一次"粗粒度索引"。
- 分区裁剪能不能生效，取决于条件写法：直接对分区键列（`created_at`）做比较，
  裁剪生效；一旦把这一列包在函数里（哪怕是和分区定义一模一样的 `YEAR()`），
  优化器就没法再做这个推断，`partitions` 列会退化成列出全部分区——这和
  [隐式类型转换让索引失效](../../beginner/03-implicit-type-conversion/) 是
  同一类问题：只要列被函数/表达式包住，很多基于"列本身"的优化都会失效。
- `ALTER TABLE ... DROP PARTITION` 直接在文件系统层面丢弃整个分区对应的
  数据文件，不管这个分区里有多少行，都是常数时间操作；普通 `DELETE ...
  WHERE` 得老老实实逐行定位、加锁、删除、写 undo log，耗时和要删的行数成
  正比。这也是分区表在"定期清理历史数据"场景里最大的价值——把一个 O(n) 的
  删除变成 O(1)。

## 复现

```bash
../../client.sh < demo.sql
```

在 200 万行、按年分成四个分区（每个约 50 万行）的表上：

- 条件直接写 `created_at BETWEEN ...`：`EXPLAIN` 的 `partitions` 列只有
  `p2024` 一个。
- 条件写成 `YEAR(created_at) = 2024`：`partitions` 列变成
  `p2023,p2024,p2025,pmax`，四个全列出来了——裁剪失效。
- `DROP PARTITION p2023`（约 50 万行）：耗时几毫秒。
- `DELETE ... WHERE` 删同量级的 `p2024`（约 50 万行）：耗时几百毫秒，比
  `DROP PARTITION` 慢了一到两个数量级。

## 结论

- 分区表适合"数据天然按某个维度分片、经常整块整块地过期/归档"的场景，
  典型代表是按时间分区的日志表、流水表；不适合"只是想让某条 `SELECT` 更快"
  这种目的——真正需要的往往还是索引，分区裁剪只是锦上添花。
- 上分区表之前先确认业务的查询模式：如果大部分查询都不带分区键做过滤，
  裁剪用不上，反而多了"每个分区都要维护自己的索引"这类额外开销。
- 想清理历史数据，优先设计成能用 `DROP PARTITION` 的分区方案，而不是定时任务
  跑大 `DELETE`——后者不仅慢，还会在 InnoDB 里产生大量 undo log 和锁竞争，
  `DROP PARTITION` 几乎没有这些副作用。
