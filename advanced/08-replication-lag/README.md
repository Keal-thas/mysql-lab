# 主从复制延迟的最小可复现 demo

## 你会学到什么

从库不是瞬间同步的——主库上一条语句提交之后，从库要先通过网络收到它、写进
中继日志，再重放一遍，这中间有真实的延迟。这个 demo 搭一个从零开始的从库，
往主库灌一大批数据造出肉眼可见的延迟，再实测它追上来要多久。

## 环境准备：从库不随默认的 `docker compose up -d` 启动

`docker-compose.yml` 里的 `mysql-replica` 服务用 `profiles: ["replica"]`
隔离，平时不占资源，只在需要时手动启动：

```bash
docker compose --profile replica up -d mysql-replica
```

## 原理

- MySQL 的经典复制流程：主库把每个事务写进 binlog → 从库的 IO 线程通过网络
  把这些 binlog 事件拉过来，写进本地的中继日志（relay log）→ 从库的 SQL 线程
  读中继日志、把事件重放到自己的数据上。**这是两个独立线程、两个独立的
  异步步骤**，主库提交和从库真正应用之间必然有时间差。
- `SHOW REPLICA STATUS` 里的 `Seconds_Behind_Source` 就是量化这个延迟的字段：
  SQL 线程正在应用的事件，和它在主库上产生的时间戳之间差了多少秒。这个值是
  从库自己估算的，网络问题、从库硬件比主库弱、从库同时在跑别的负载，都会让
  它变大。
- 制造延迟最简单的办法就是让主库短时间内产生大量 binlog：这个 demo 一次性
  插入 200 万行，从库的 IO 线程能很快把 binlog 拉过来，但 SQL 线程要一行一行
  重放这些 `INSERT`，跟不上主库写入的速度，`Seconds_Behind_Source` 就会先冲
  上去，再慢慢降回 0。

## 复现

```bash
./setup_replication.sh
```

这一步启动 `mysql-replica`、在主库建一个复制账号、记下主库当前的 binlog
位置，然后让从库从这个位置开始拉取——因为是全新的从库、没有主库的历史数据，
所以复制关系建立后只会同步"从现在起"的变更，不会自动补全之前就存在的数据
（这也是从零搭从库时必须注意的一点：生产上通常是先用 `mysqldump`/物理备份
把主库当前数据搬到从库，再从备份对应的那个 binlog 位置开始接上复制）。

```bash
./generate_lag.sh
```

往主库灌 200 万行，然后每 2 秒查一次从库的 `Seconds_Behind_Source`，实测数字
会先涨到个位数的秒级，再降回 0；脚本最后对比主从两边的行数，追上之后应该
完全一致。

用完之后（不想让从库继续占着资源）：

```bash
./teardown.sh
```

只会删除 `mysql-replica` 这一个容器，不影响 `mysql`/`adminer`/`dozzle`/
`docs` 这些一直在跑的服务——**千万不要在这个仓库目录下跑裸的 `docker compose
down`**：它会把整个项目（包括主库）一起停掉，不会只停 `--profile` 选中的那
一个服务，这是写这个 demo 时真的踩到的坑。

## 结论

- 复制延迟是异步复制天生的代价，不是 bug；关键是要能监控到它——生产上一般
  会对 `Seconds_Behind_Source` 设告警阈值，超过就说明从库可能已经不适合拿来
  分担读流量了（读到的可能是几秒甚至几十秒前的旧数据）。
- 延迟的根本原因通常是"从库单线程重放跟不上主库的多连接并发写入"——MySQL
  从 5.7 起支持多线程并行复制（按库或按事务分组），能缓解但不能完全消除
  这个问题，本质上从库还是要做和主库等量的写工作。
- 从零搭从库、不提前迁移历史数据，复制关系一样能建立成功，只是从库上不会有
  接入前的旧数据——这个细节很容易被忽略，生产环境务必先用一致性备份对齐
  数据，再对上正确的 binlog 位置。
